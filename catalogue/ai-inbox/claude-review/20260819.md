## 2. Findings

Severity is about this repo's risk, not CVSS.

### F1 · HIGH · Admin login returns 500 wherever `admin_login_attempts` is missing

`backend/src/modules/auth/service.rs:152-166`, `backend/src/db/admin.rs:88-107`,
`backend/src/modules/auth/service.rs:307-313`

`login_is_throttled` runs first and uses `?`, so a DB error is not degraded — it propagates through
`map_auth_lookup_error`, which returns `INTERNAL_SERVER_ERROR` / "Unable to verify admin credentials."
The table only exists after `0036` is applied. It is applied **nowhere**: not on production
(`docs/1.1`), and not on the local dev DB (`to_regclass` → NULL). Right now this tree cannot log an
admin in against the local database at all, and deploying the binary before the migration would take
`/admin` offline for everyone, including the owner.

Failing closed is the correct instinct for a throttle, but it must not be the failure mode for a
*missing* throttle. Ordering requirement for M1: apply `0036`, verify the table, **then** ship the
binary. Consider also treating a `relation does not exist` error as "throttle unavailable, log loudly,
allow" — or gating the whole throttle behind a startup probe — so a migration slip degrades security
rather than availability.

### F2 · MEDIUM · Per-client throttle bucket is keyed on an attacker-controlled header

`backend/src/modules/auth/service.rs:69-88`

```rust
    let forwarded = headers
        .get("x-forwarded-for")
        .and_then(|value| value.to_str().ok())
        .and_then(|value| value.split(',').next())
```

Caddy's `reverse_proxy` **appends** to an inbound `X-Forwarded-For` rather than replacing it, so a
client-supplied value survives as the *first* element — exactly the one taken here. A caller sending
`X-Forwarded-For: 203.0.113.<n>` gets a fresh bucket per request, so `MAX_LOGINS_PER_CLIENT = 20`
(`service.rs:65`) is not a limit. `X-Real-IP` (`service.rs:83`) is equally forgeable.

What this does and does not cost:

- The per-username cap of 5 is **unaffected** — `username_key` comes from the request body, not a header
  — so single-account brute force is still stopped. That is the primary control and it holds.
- The client cap exists to stop *spraying across many usernames* from one source, and that defence is
  void.
- It also unbounds `admin_login_attempts` growth: the throttle short-circuits before the `INSERT`
  (`service.rs:104-114`), so rows are normally self-limiting, but a fresh spoofed `client_key` buys 20
  more inserts against 20 fresh usernames, repeatable indefinitely.

Recommended fix, **not applied** — for the production topology (Caddy on the Lightsail host is the
internet-facing edge; the only `cloudflared` in the tree is a `trycloudflare.com` quick tunnel started
from a Windows dev box for HitPay sandbox UAT, `deploy/cloudflared-20260813-072226.err.log:1-11`), the
trustworthy element is the **last**, not the first:

```rust
        .and_then(|value| value.rsplit(',').next())
```

I did not make this edit. It changes the auth path's behaviour and its correctness depends on the number
of trusted proxy hops actually in front of the backend, which the repo alone cannot settle. If a second
proxy is ever inserted, `rsplit` collapses every caller into one shared bucket and 20 attempts per 15
minutes becomes a global admin lockout — a worse failure than the one being fixed. The durable form is a
`TRUSTED_PROXY_HOPS` setting selecting the Nth-from-last element. This also is not urgent to ship blind:
per **F1** / Fact 5, the throttle is not live anywhere yet, so there is no deployed control being
bypassed today. Confirm the hop count, then patch and test together.

Note `deploy/hitpay-sandbox-tunnel.nginx.conf:10-12` sets `Host` and `X-Forwarded-Proto` but never
`X-Forwarded-For`, with `proxy_pass_request_headers on` — in that sandbox path the header is passed
through wholly unfiltered. Sandbox-only, but worth knowing before that config is reused.

### F3 · MEDIUM · Username lockout is a denial-of-service primitive with no unlock path

`backend/src/modules/auth/service.rs:152-166`, `backend/migrations/0036_admin_login_throttle.sql`

Five failures in 15 minutes lock a named admin regardless of where they came from, and the correct
password is refused for the remainder of the window — `backend/tests/admin_api.rs:99-108` asserts exactly
that. Nothing in the tree clears `admin_login_attempts`: `grep` finds only the migration, three queries
in `backend/src/db/admin.rs:88-145`, and no pruning job, retention policy, admin surface, or runbook.
Combined with **F2**, an unauthenticated attacker can hold `admin` locked out indefinitely for the cost
of one request per 15 minutes.

Worth deciding explicitly rather than inheriting: exponential backoff instead of a hard window, and/or an
operator unlock. Add a retention sweep either way — the table grows monotonically.

### F4 · MEDIUM · Admin session tokens stored in plaintext (pre-existing)

`backend/src/db/admin.rs:150-162` (insert), `backend/src/db/admin.rs:179-206` (literal `token = $1`
compare)

Sessions live 7 days. Any read of the database — a backup, a dump, a restore rehearsal, a future SQL
injection — yields directly usable admin sessions. Store `sha256(token)` and compare the hash; the token
itself never needs to be at rest.

### F5 · MEDIUM · MFA is schema-only and enforced nowhere (pre-existing)

`backend/migrations/0026_account_mfa.sql`, `backend/src/db/admin.rs:179-206`, `backend/src/routes.rs`

`admin_mfa_factors`, `admin_mfa_challenges`, `admin_mfa_recovery_codes` and
`admin_sessions.mfa_verified_at` all exist (confirmed present in the local DB), but no code reads or
enforces them. `authenticate_admin_session` does not look at `mfa_verified_at`; `routes.rs` has no MFA
route; there is no `modules/mfa`. The only references in `backend/src` are the readiness probe's column
list, `backend/src/modules/health/controller.rs:29-43`. The admin console is therefore single-factor
password auth on the public internet — which is what makes F1/F2/F3 matter more than they otherwise
would.

### F10 · LOW · The Caddy guard is narrower than it reads

`deploy/ekowayhardware.Caddyfile:15-21`, `backend/src/routes.rs:270-275`

Related, and the reason this holds: `backend/src/modules/orders/controller.rs:135-160` gates the legacy

### F11 · LOW · Reset script forges an admin session, bypassing login, throttle, and MFA

`scripts/reset-local-admin-password.ps1:53-57` (untracked)

```powershell
    $insertSession = "INSERT INTO admin_sessions(token, admin_user_id, expires_at, mfa_verified_at) VALUES ('$token', $adminId, now() + interval '5 minutes', now());"
```

The design is defensible — it needs DB access, which already implies full compromise; the token is
32 bytes from a CSPRNG, the session lasts 5 minutes, and `finally` deletes it. Two rough edges:
`-ApiBaseUrl` and `-DatabaseContainer` are free parameters, so nothing but convention keeps this pointed
at localhost; and the token is interpolated into a `psql -c` argument, making it visible in process
listings and PowerShell history for the life of the call. Pipe the SQL over stdin and pin the parameters
to local defaults.

## 3. Missing tests

Ordered by what would have caught the findings above.

**Blocking — these guard things that can take the site down or open a control**

1. **Throttle against a missing table.** No test asserts what `POST /api/admin/login` does when
   `admin_login_attempts` does not exist. This is **F1**, the highest-severity finding, and it is
   invisible to the suite because `#[sqlx::test]` always applies every migration. Needs a test that
   drops the table (or points at a pool without it) and pins the intended behaviour — today's answer is
   a 500.
2. **Client-key derivation.** `client_key_from_headers` / `forwarded_client_key`
   (`service.rs:69-88`) have no unit test at all. Wanted: first-vs-last `X-Forwarded-For` element,
   `X-Real-IP` fallback, whitespace, empty header, absent header → `"unknown"`. A table test here
   converts **F2** from a judgement call into a decision recorded in code.
3. **The per-client cap.** `MAX_LOGINS_PER_CLIENT = 20` is completely uncovered —
   `backend/tests/admin_api.rs:74` exercises only the per-username path. Needs: 20 attempts spread across
   *different* usernames from one client key → 429; and the same 20 with a rotating spoofed
   `X-Forwarded-For` → currently *not* throttled, which is the regression test for whichever fix lands.

**Important — behaviour this review had to verify by reading**

4. **Throttle window expiry.** Nothing asserts that the lock *releases*. A test that back-dates
   `created_at` beyond 15 minutes and confirms a correct password succeeds would pin
   `LOGIN_WINDOW_MINUTES` and catch the interval cast in `db/admin.rs:88-107` silently becoming a no-op.
5. **Throttle isolation between usernames.** No test proves 5 failures against `admin-a` leave `admin-b`
   loginable. Cheap, and it is the property that keeps **F3** merely bad rather than total.
6. **Delivery gate on the two checkout routes.** `backend/tests/storefront_api.rs:106` covers
   `/api/checkout/quote` only. The `ensure_public_checkout_fulfillment` call added to
   `payments/service.rs:137` in this tree — the gateway path — has **no** test, nor does
   `orders/controller.rs:163`. Also missing: the positive case, `PUBLIC_DELIVERY_ENABLED=true` →
   delivery accepted, which is what will actually be exercised when delivery opens.
7. **Payment activation gate on the legacy route.** `orders/controller.rs:135-147` refuses in
   `disabled`/`controlled`, and `:150-160` returns 410 under `APP_ENV=production`. `activation.rs` has
   in-module tests for mode resolution, but the legacy-route gate itself is untested end-to-end. Both
   branches are load-bearing for "payments are off".
8. **Front-end flag matrix.** No test asserts that with `VITE_ENABLE_CARD_PAY` unset the submit handler
   takes the WhatsApp branch and never calls `onCheckout` (`App.tsx:5257-5270`). 67 front-end tests pass
   (`docs/p4-public-surfaces-status-2026-08-18.md`) but none pin the commercial lock that is currently
   holding the store closed.

**Worth adding while nearby**

9. **Session token at rest.** A test asserting `admin_sessions.token` never equals the bearer token would
   fail today and pass after **F4** is fixed — a good way to schedule that work.
10. **Caddyfile routing.** No test or CI check covers `deploy/ekowayhardware.Caddyfile`. A
    `caddy validate` step plus a table of path/method → expected status (`POST /api/checkout` → 503,
    `POST /api/checkout/quote` → backend) would keep **F10** from drifting when the guard is eventually
    lifted.
11. **Build-artifact freshness.** Nothing detects **F7**. A CI step that rebuilds `frontend` and fails if
    the deployed asset hash differs — or simply refuses to deploy a `dist/` older than the newest file in
    `frontend/src/` — closes a whole class of "shipped the pre-lock bundle".
